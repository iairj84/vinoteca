# Insight Redesign — step-by-step plan for the coding agent

Repo: `iairj84/wine-verdict` (Android, Kotlin + Compose). Save this file as `docs/INSIGHT_REDESIGN.md`.

## Why we're doing this

Scans and recommendations are accurate but not useful. Test case (restaurant list, 31 wines, profile = "red, smooth, dry, restrained oak"): the app ranked the **first three sparkling lines on the page** as "best first". A free text model (Groq `gpt-oss-120b`) given the same list as plain text plus a short taste profile picked Bierzo Mencía / Rioja Crianza and correctly skipped the Priorats. Causes found in the code:

1. **Truncated judgement.** `judgeList()` in `ui/ScanScreen.kt` calls `Prompts.listJudge` with `maxTokens = 800` and `Thinking.OFF`, but asks for one line per wine (5 fields, two of them up to 14 words). 31 wines need ~1,500+ tokens, so the answer is cut off partway down the page and only the first lines (sparkling) get judged.
2. **Every wine ranked, no reasoning.** Ranking all 31 lines with thinking off spreads a small model thin. Diners need 2–3 picks and a few skips, explained well.
3. **The taste file forbids knowledge.** `mytaste.md` (generated by `data/PalateFile.kt`) is ~1,800 words of meta-rules and says "Facts about a bottle… never from memory" and "No number appears in an answer that isn't in the bottle record", which contradicts `listJudge`'s "Use what you know". Lists never print ABV or oak, so "Unknown is not a pass" makes every red fail or go unknown.
4. **Code decides the verdict with no data.** `data/BuyAdvice.kt` builds Buy/Look/Leave from sugar/oak/ABV gates that are almost always UNKNOWN on a list.
5. **The quick start collects settings, not taste.** It infers "13.5% or under" from "avoid strong", which contradicts the user's 5★ Zinfandel.

## Target design

```
Photo ──► READ (vision, strict, thinking OFF) ──► list of wines (text)
                                                    │
taste brief (short) + cellar summary ───────────────┤
                                                    ▼
                                   ADVISE (text model, thinking MEDIUM)
                                   2–3 picks + skips + glass pick, real reasons
                                                    │
                                                    ▼
                                   VALIDATE (code): every pick = a real line
                                                    │
                                                    ▼
                                   Cards (+ optional "Verify" via WebLookup)
```

Rules for the ADVISE step:
- Use general wine knowledge about regions, grapes, styles and producers; say "typically" when it isn't printed on the list/label.
- Producer- or vintage-specific details (months in oak, blend %, exact ABV) only when they come from the label, the list or `WebLookup` results — otherwise leave them out.
- Recommend by referencing list line numbers, never by retyping names.
- Gates are preferences with typical values, not pass/fail on missing data.

## How to run these steps

- Work on a new branch: `git checkout -b insight-redesign`.
- **One step per chat.** Start each chat with: *"Read AGENTS.md and docs/INSIGHT_REDESIGN.md, then do Step N only."*
- After each step: build (`./gradlew :app:assembleDebug`), run tests (`./gradlew :app:testDebugUnitTest`), commit with a message that explains why, then stop and report.
- Suggested models: DeepSeek V4.1 Flash for code changes; MiMo 2.6 Pro for review.

## Step 2 — Short taste brief (stop forbidding knowledge)

**Prompt:**
> In `data/PalateFile.kt` add `fun brief(profile: PalateProfile, rules: PalateRules, loved: List<Wine>, disliked: List<Wine>): String` that renders a SHORT taste brief (target 120–250 words, hard cap 1,500 characters) in plain first-person prose, using the template in docs/INSIGHT_REDESIGN.md Step 2. Include: what I usually drink; style words; sweetness; oak and alcohol as preferences ("prefer", not gates); budget as retail AND as a restaurant range (retail × 2.5–3.5); up to 4 loved bottles with their flavour tags; up to 3 disliked bottles; a one-line "what links them" only if the user wrote one. Do NOT include confidence tables, precedence rules, signal weights, gate tables, or any line telling the model not to use its knowledge. Make `TasteStore.brief()` return this brief (generated from the stored profile and cellar) for every model request; keep the full `mytaste.md` as the user-facing/editable file. If the user has hand-edited text in the advanced editor, append their "## Notes" section (max 600 chars) to the brief. Add unit tests for length cap and for the absence of the words "never from memory" and "Unknown is not a pass". Commit.

Brief template:
```
I mostly drink {pours}. I like {style words}; {sweetness}. I prefer {oak preference}
and {alcohol preference} — preferences, not rules.
Bottles I loved: {producer wine vintage, region — flavour tags} (up to 4)
Bottles I didn't enjoy: {…} (up to 3, or omit)
{user's own "what links them" line, if any}
Budget: {retail band} retail, about {restaurant band} on a restaurant list.
I want to know where a wine comes from and why it tastes the way it does.
{adventure line, e.g. "Surprise me when the reason is good."}
```

**Done when:** the brief for the current profile reads like the example in the doc and is under 1,500 chars; tests pass.

## Step 5 — New ADVISE prompt for wine lists (replaces `listJudge`)

**Prompt:**
> In `ai/Prompts.kt` add `fun listAdvice(brief: String, cellarSummary: String, currency: String, bottles: List<ScannedLabel>, food: String?): String` using the prompt text in docs/INSIGHT_REDESIGN.md Step 5. Wines are passed as numbered lines including section/type, grapes, region, glass and bottle price. In `ui/ScanScreen.kt` replace the `judgeList()` call with an advice call: `vision = false`, `jsonMode = false`, `thinking = Thinking.MEDIUM`, `temperature = 0.4`, `maxTokens = 1_800`, timeout 60 s. Keep `listJudge` in the code for one release as a fallback when the advice call fails. Commit.

Prompt text:
```
You are an experienced sommelier helping one diner order from a restaurant wine list.
Read the WHOLE list before deciding. Then recommend what this diner should order.

Knowledge rules:
- Use your general knowledge of regions, grapes, styles, vintages and producers.
  When something is typical rather than printed on the list, say "typically".
- Do not state producer-specific specifics you cannot be sure of (months in oak,
  blend percentages, exact alcohol, scores, awards). Region- and grape-level
  reasoning is preferred: climate, elevation, soils, grape character, ageing style.
- Never invent a wine, price or vintage. Refer to wines ONLY by their line number.
- A wine's colour/style is the section it is listed under. A wine listed under
  ROSADO is a rosé even if the grape is usually red.

Taste: read MY TASTE below. Treat oak, alcohol and sweetness as preferences.
Connect your reasons to the bottles I loved when you can.
Budget: prefer bottles inside my restaurant range; go above it only with a reason.

Reply in exactly this format, nothing before or after:

PICK 1 | <line number> | <one-line headline>
WHY: <2–4 sentences: what it is, why it tastes that way, why it suits me>
PICK 2 | <line number> | <headline>
WHY: <2–4 sentences>
PICK 3 | <line number> | <headline>          (optional)
WHY: <2–4 sentences>
GLASS | <line number> | <one sentence>        (best by-the-glass option, if any)
SKIP | <line number> | <one sentence why>     (2–4 lines, the tempting wrong choices)
NOTE: <optional one sentence, e.g. a splurge worth knowing about>

MY TASTE
{brief}

WHAT I ALREADY OWN (summary)
{cellarSummary}

FOOD (if given)
{food}

WINES
{numbered lines}
```

**Done when:** the debug panel shows a complete PICK/WHY/SKIP answer for the 31-wine list.

## Step 6 — Parse and validate the advice

**Prompt:**
> In `ai/ScanParsing.kt` add `fun parseAdvice(raw: String, read: SceneScan): ListAdvice?` with data classes `ListAdvice(picks: List<AdvicePick>, glass: AdvicePick?, skips: List<AdvicePick>, note: String)` and `AdvicePick(index: Int, headline: String, why: String)`. Parsing rules: accept any case and surrounding whitespace; join multi-line WHY text until the next tag; ignore lines that are not tags. Validation in code: (a) line number must exist in `read.bottles`; drop otherwise; (b) a GLASS pick must have a glass price; drop otherwise; (c) if a headline or WHY calls a wine "red" but its listed type is rosé/white/sparkling (or vice versa), drop the pick and log it in the debug panel; (d) drop duplicate line numbers; (e) return null if no valid PICK remains, so the caller falls back to `listJudge`. Add unit tests using the fixture from Step 1 and hand-written raw answers, including one that recommends line 16 ('Zestos', listed under ROSADO) as "a red by the glass" and must be dropped. Commit.

**Done when:** tests cover valid answer, invalid line number, colour mismatch, missing glass price, duplicates.

Three departures from the prompt above, all deliberate:

- **No "More" collapse.** The prompt asks for 2–4 sentences, so the WHY is shown whole. A chatty
  answer runs long rather than truncating, and length is a validator's job, not a fold's.
- **The glass pick is a block inside the advice card**, not its own card: it is one line competing
  with the picks beside it, not a separate recommendation.
- **The Glass/Bottle/Not sure toggle was restored afterwards** (`b138047`): replacing the ranked
  section took the pour choice with it, and choosing a pour is the first question at a table. Glass
  keeps only picks with a printed glass price, Bottle hides the by-the-glass answer, and the block
  starts on neither, showing both with a line that says so.

The colour check from Step 6 gained one rule: a colour word introduced by `like`, `than`, `as` or
`unlike` is a comparison, not a claim about this wine, so "drinks like a white but with the tannin
of a red" no longer drops a red.

## Step 8 — Pick the right text model for advice

**Prompt:**
> In `ai/AiProvider.kt` add `defaultAdviceModels` per provider: Groq `openai/gpt-oss-120b`; Gemini a non-Lite Flash model (verify the current id with Settings → Test connection and use what the key lists); OpenRouter keep the current free model. Add an "Advice model" field per provider in Settings (same pattern as text/vision models). The advice call (Step 5) and the chat use the advice model; scans/reads keep their current models. Default provider order for advice: Groq first if it has a key, else Gemini. Make sure `Thinking.MEDIUM` maps correctly per provider in `AiClient.thinkingValue` and that a model rejecting the reasoning field gets one retry without it (existing behaviour — confirm). Update README "Keys" table. Commit.

**Done when:** debug panel shows the advice request going to `gpt-oss-120b` (or the configured model) with reasoning on.

**Shipped** (`b138047`). `AiProvider.defaultAdviceModels`, `SettingsStore.adviceModel()` under the
`advice.<provider>` key, an "Advice model" field on every provider card, and `AiClient.complete(
advice = true)` used by the Step 5 advice call and by the chat. Reads keep the vision and chat
models and the primary-provider order. The debug panel's request row shows the provider and model
that answered the advice call, with reasoning on.

`AiProvider.adviceOrder` is a pure function — Groq, then Gemini, then OpenRouter — and
`SettingsStore.adviceProviders` delegates to it. It is written that way because this is exactly the
ordering that gets "cleaned up" into `configuredProviders` later, which would send a 4,000-token
reasoning call to whichever provider was last chosen for photos.

`Thinking.MEDIUM` maps to `medium` for Groq and Gemini and omits the field on OpenRouter, and the
one-shot 400 retry (plainest payload, one image, no reasoning field) is still in `AiClient.attempt`.

Two departures:

- **Gemini keeps its Lite id.** The prompt asked for a non-Lite Flash model, but nobody has a
  verified id for this key, and an invented one is a 404 the user has to debug. The field exists so
  they can set the right id without an update.
- **OpenRouter is unchanged** — its free model is the only one the key reaches.

Not verified: a live advice call on Gemini's slot, since there is no Gemini key on the machine that
built this, so only the Groq default is measured. And Groq's free tier allows 8,000 tokens a
minute: one advice call (~2,000 prompt, up to ~5,800 completion with the reasoning reserve) can use
the whole minute, with no room for a retry. Groq leading therefore suits one list per sitting.

**Measured** (`LiveChatBudgetTest`, Groq `openai/gpt-oss-120b`, a 121-message conversation, sent
through the real `chatPayload` and `chatHistory`):

| history budget | digest | window | prompt | completion | outcome |
|---|---|---|---|---|---|
| 2,000 tokens | 55 bottles | 26 of 121 messages, 7,335 chars | **3,908** | 794 (628 reasoning) | 200, 692 tokens left in the minute |
| 8,000 tokens | 140 bottles | 105 of 121 messages, 30,416 chars | ~10,454 est. | — | **HTTP 413**: larger than the minute |

Every number here comes from one `-Plive` sweep of the merged harness, each case run on its own
minute — `thin`, `wide` and `rescue` back to back would spend more than the 8,000-token minute and
the later results would be 429s.

The thin window is about 1,925 real tokens; chars/4 underestimates by roughly 6%, so a budget is
slightly tighter than its name. One thin turn costs ~4,700 of the 8,000 and a second turn in the
same minute cannot fit — and trimming the history further does not buy one, because the 55-bottle
digest is ~1,700 of the 2,030-token system prompt. The wide window is for Gemini's 250,000-token
minute only; on Groq it is refused outright.

**Rescue measured** (`rescueAfterA413`, same harness): a 72,571-character body — 201 turns, ~17,462
estimated tokens — came back **413**. The same conversation through `leanPayload` (7,843 chars, the
newest turn only) answered **200**: prompt 2,184, completion 839 of which 681 was reasoning,
5,485 tokens left in the minute. Dropping the history turns a refusal into an answer for ~38% of
the minute, so the rescue is worth its retry.

The window is now sized from the **thinnest configured provider**, not from the one that leads.
Sized from the lead, a dual-key install sent 8,000 tokens of history to Gemini and, when Gemini was
rate limited and Groq answered, got a 413 instead of an answer. The cost is context on the lead — a
dual-key install always sends the thin window — and it is paid deliberately: an answer with less
history beats a 413. `chatBudget` holds both numbers (history and digest) so they cannot drift
apart, and a test pins the dual-key case.

**Follow-up** (`AiJob`, after `b138047`). The chat did not keep that order. A chat turn resends the
brief, the cellar and every earlier message at 2,500 tokens of headroom, so two or three turns
empty Groq's free minute — and a conversation is where the user keeps going. `AiClient.complete`
now takes `job: AiJob` (`READ`, `ADVICE`, `CHAT`) instead of an `advice` flag; `READ` keeps the
text/vision models and the primary order, `ADVICE` leads with Groq, `CHAT` with Gemini, and both use
the advice model. A review pass then collapsed the two named order functions and the two
`SettingsStore` properties that wrapped them into one `AiProvider.order(job, providers)`; the
provider's own list hands it `configuredProviders`, so there is one place where "who answers first"
is decided. A request carrying a photo takes the
vision model first whichever job asked — the Step 8 version would have sent a chat photo to a
text-only advice model.

## Step 10 — Bottle insight ("why it tastes this way") with cache

**Prompt:**
> After a single-bottle label is read and confirmed, run a separate text-only `Prompts.bottleInsight(label: ScannedLabel, brief: String)` call (advice model, `Thinking.MEDIUM`, `jsonMode = true`) that returns JSON matching `WineInsight` in docs/INSIGHT_REDESIGN.md Step 10. Keep the existing "Look up tasting notes" (WebLookup) button; label its output as "From the web" with sources. Migrate existing records safely (field defaults to null). Commit.

WineInsight:
```json
{
  "headline": "string",
  "why_it_tastes_this_way": [
    { "claim": "cause -> effect sentence", "basis": "region|grape|vintage|producer|style", "confidence": "high|medium|low" }
  ],
  "tasting_profile": { "body": "light|medium|full", "tannin": "low|medium|high", "acidity": "low|medium|high", "notes": ["string"] },
  "drinking_window": { "from": 2026, "to": 2032, "confidence": "high|medium|low" },
  "food_pairings": ["string"],
  "for_you": "1–2 sentences linking to my loved bottles, or null"
}
```
Insight prompt rules: reason region → grape → vintage → producer; producer claims only when confident, else omit; no scores, awards or prices; every claim states a cause and an effect.

**Done when:** scanning a bottle shows a "why" section; rescanning the same wine shows it instantly with no AI request in the debug panel.

- **At the confirmation, not at the read.** A single bottle is confirmed in the editor, so the save

- **The stored answer keeps the schema's key names.** `@SerialName` pins `why_it_tastes_this_way`,

## After Step 11 — the list advice no longer waits for the phone's OCR

**Why.** The advice was reached only when the phone's own OCR produced the page. A device without the
ML Kit text module gets no advice at all, however legible the list: every list scan in this document
shows `on-device OCR · 0 chars · failed` and then a ranking from the read's own order, unexplained.
That is the app's best answer withheld from the page it is best at, because a different component was
missing.

**What changed.** `judgeList(read, rankIfUnanswered)` runs for a list the model read as well, under the
same budget rules — `remainingMs() > 15_000` before the call, the 60 s cap — and the same single retry
for a 503 inside `adviceAnswer`. The deadline now moves out to `ADVICE_DEADLINE_MS` inside
`adviceAttempt` itself, so the rule is written once, at the call that needs the longer window: a page
that had to be read first must not fail on the budget the read was given. What is deliberately not
copied is the ranking call: a model-read list already carries its own order, so a second 4,000-token
`listJudge` would buy a ranking that is already on screen. The phone path keeps it, because a failed
answer there leaves no ranking at all.

**Reviewed, same day — no double call.** The two advice hooks are now one guard and one `when` on the
scene, so only one of them can fire per scan. The list hook's `onPhone == null` is exactly "the list
answer has not been asked yet": the phone branch always asks it first, so there is no path that asks
twice, and a page that fell through to the model's read has already spent both its attempts. The one
case left without advice is the intended one — OCR worked, the answer failed twice, and a third
4,000-token call in the same free-tier minute would only 429.

**Measured, 2026-11-26** (emulator, real Gemini key, the 26-wine `wine-list.png` picked from the
gallery): `on-device OCR · ML Kit · 0 chars · failed` → `read the page · Gemini · 5,673 chars ·
9.9 s` → `advice · Gemini · gemini-3.1-flash-lite · 1,696 chars · 5.3 s`. The block rendered
`Order this` (Vall Llach 'Embruix'), `Second`, `Third` ('Stimatum' Akoi…), a `By the glass` card
(Olabarri Reserva, `USD 58.00 bottle · USD 15.00 glass`), `Skip` with its reason, and the note about
the Tondonia magnum. No retry row: the first attempt answered. The same photo previously produced
"Basic ranking" and no picks at all. Run again after the review refactor: `read the page · Gemini ·
5,726 chars · 8.4 s` → one `advice` row, `1,721 chars · 5.2 s`, block rendered — the refactor is
behaviour-neutral, and the panel showed a single advice row (no retry) both times.

**Failure path, forced** (same day). The advice was made to fail without touching code: the Gemini
card's *Advice model* was set to `gemini-2.5-flash` — reads keep `gemini-3.1-flash-lite`, and free-tier
minutes are counted per model — and that model's minute was then spent from the host, so every advice
call answered 429: a real retryable failure from the real provider. Panel: `advice · 0 chars · 115 ms ·
failed: Google Gemini rate limit hit (429)`, then `advice (retry) · 0 chars · 20,139 ms · failed: …
(429)` — the 20 s is the rate limiter's penalty wait before the second attempt, which `budgetMs`
allowed and `adviceTimedOut` did not block. **No `judge (fallback)` row**: `rankIfUnanswered = false`
returned null without spending a second 4,000-token call. On screen, no `What to order` block at all —
a plain caption, "Basic ranking — the advice answer did not come back, so this is the model's order for
the wines it could judge", then "Worth ordering, best first" rendered from the read
(`ListPicks.Basis.READ`, 5,279 characters) with the pour toggle and no half-drawn cards. Setting the
advice model back to `gemini-3.1-flash-lite` and scanning the same photo returned `What to order`
again, so the failure was the setting and the quota, not the code.

The run also exposed a blemish, since fixed in its own commit: failed rows read `no provider`, because
the client reported who answered only when one did. `complete()` now reports each request as it goes
out (`onTry`), so a failed row names the provider and model it asked, which is the difference between
"quota" and "bad key". The same answer exposed a second one: its `SKIP | 11, 25, 26 | …` row was
dropped as "no such line on the page" because the digits were glued into 112526 — a skip tag now takes
every number on it.

Still not verified: a *503* rather than a 429 (both take the same `retryable` branch); the phone-read
path on hardware with working OCR; and Groq as the advice provider.
